## База данных в osago-aggregator
- osago-aggregator будет иметь отдельное бд, где мы будем хранить
    - ID заявки
    - ID каждой внешней заявки в страховой
    - статусы (создана, в ожидании, получен оффер, таймаут)
    - сами офферы
    - таблица для transactional outbox

## Типы интеграций
- core-app и osago-aggregator будут взаимодействовать через kafka.   
    - core-app будет публиковать событие заявки на ОСАГО, osago-aggregator читать это сообщение, создавать у себя в бд заявку и отправлять запросы в страховые компании. 
    - По мере поступления ответов от страховых компаний, osago-aggregator будет обновлять данные заявки в бд и таблице outbox, которая будет считываться для публикации события предложений. 
    - сообщения будут иметь ключ, равный user_id или session_id, чтобы сообщение считывалось нужным инстансом core-app, держащим websocket соединение с фронтом.

- core-app и фронт будут взаимодействовать через REST для изначального запроса создания заявки на ОСАГА и через websocket для обновления UI по мере поступления ответов от страховых компаний.

## Паттерны отказоустойчивости
- при взаимодействии core-app и osago-aggregator:
    - retry и DLQ (dead letter queue. Заведём под это отдельный топик, который потом будет отдельно анализировать). Мы отключим auto.commit для concumer'ов. Например, osago-aggregator читает сообщение, оно автоматически не будет помечаться, как прочитанное, отправляет запрос в страховую, запрос не проходит из-за ошибки сети. Будет попытка прочесть сообщение снова (с нарастающей задержкой перед прочтением). После удачного запроса в страховую помечаем сообщение как прочитанное. Если неудачныых попыток станет 3, то переносим сообщение в DLQ.

- при взаимодействии osago-aggregator и страховыми:
    - retry. Делаем 3 попытки получить ответ с нарастающей задержкой. Если неудачныых попыток станет 3, то переносим сообщение в DLQ.
    - timeout. По условию у нас максимальное время ожидания решения от страховой компании равно 60 секунд. Поэтому с запасом на задержки (отправка, чтение, обработка сообщений) сделаем timeout 55 секунд.
    - circuit breaker. Если страховая не отвечает, то закрываем breaker на некоторое время, логируем инцидент, потом постепенно пробуем открывать breaker.
    - rate limiting. Делаем ограничение на количество запросов в каждую страховую, чтобы не получить бан.

- при взаимодействии core-app и фронта:
    - timeout на REST API запросы. Если не получаем ответ от core-app в течение нескольких секунд, то показываем уведомление.
    - ping/pong и reconnect логика (heartbeat, например, каждые 30 сек) для websocket соединения.
